Model once.
Store anywhere.

Every fact in XDB is a tuple: a path, an attribute, a typed value. Tuples make records, records go into any backend, and one API and one CLI read and write them all with the same rules.

Get started View GitHub
$ go install github.com/xdb-dev/xdb/cmd/xdb@latest
The model

Everything is a tuple.

A tuple is one addressable fact. Its URI says where it lives, its attribute says what it is, and its value carries a type. There is nothing smaller, and everything larger is built from it.

Tuples make records. Records live in schemas. Schemas live in namespaces.

Tuples that share a path are a record. A record adds no data of its own: it exists when its first tuple is written and disappears when its last one is deleted. A schema groups records and decides how strictly they are checked. A namespace groups schemas by domain, app or tenant.

Every level has a URI, so every level can be read, listed, written and watched by the same verbs. That includes the tuple: get on an attribute URI returns one fact, and delete on it removes just that fact.

namespacexdb://com.example schemaxdb://com.example/posts recordxdb://com.example/posts/p-1 tuplexdb://com.example/posts/p-1#author.name

Dotted attributes unfold on output, so the record above reads back as nested JSON. The store stamps _id, _version and _updated on every record.

{ "title": "Hello", "author": { "name": "Ravi" }, "views": 42,
  "_id": "p-1", "_version": 1, "_updated": "2026-09-04T09:12:00Z" }

Nine value types.

Defined once in the model, mapped to a native column or encoding per backend. Every value has typed As* accessors, so a wrong type and a missing value are different errors.

stringintegerunsignedfloatbooleantimejsonbytesarray<T>

What a schema can say.

  • Mode. Strict rejects undeclared fields, flexible accepts anything, dynamic grows the definition as data arrives.
  • Required, indexed, unique. Required attrs cannot be deleted out of a record. Indexed and unique fields become real indexes on SQLite.
  • Arrays. Every array declares its element type. Object arrays carry the shape of their items.
  • Revisions. Every schema update is a compare-and-swap on its revision. Types and modes are immutable once set.
  • Cascade. Deleting a schema with its records is one explicit flag, never an accident.
Bring your own types

Import the model you already have.

A schema can come from a Go struct with tags, a protobuf message, or a JSON Schema document. The struct is the schema, and your types go in and come out. Diff runs the same walk without writing, and fails CI when the code and the stored schema drift apart.

types.go · your structs, not tuples
type Post struct {
    Title  string    `xdb:"title,required"`
    Author Author    `xdb:"author"`      // → author.name
    Tags   []string  `xdb:"tags"`        // → ARRAY<string>
    Views  int64     `xdb:"views"`
}

// The struct is the schema.
def, err := xdbstruct.Def[Post]("xdb://com.example/posts")
err = st.CreateSchema(ctx, def)

// Your types in, your types out.
rec, err := xdbstruct.Marshal(
    "xdb://com.example/posts/p-1", post)
err = st.CreateRecord(ctx, rec)

var got Post
rec, err = st.GetRecord(ctx, uri)
err = xdbstruct.Unmarshal(rec, &got)
shell · import shows the delta, diff --check fails CI on drift
$ xdb schemas import ./api/user.proto --ns com.example
$ xdb schemas import ./user.schema.json --ns com.example
$ xdb schemas diff ./api/user.proto --ns com.example --check
go · the same importers as a library
def, err := jsonschemaimport.Import(doc,
    jsonschemaimport.WithNamespace("com.example"))

def, err := protoimport.ImportMessage(md,
    protoimport.WithNamespace("com.example"))
Backends

The same tuple, in every database.

A backend only has to store tuples. The path becomes whatever that backend uses to address things, and the attribute and value become whatever it uses to hold them. Nothing about the model changes when the backend does.

Pick one in the config.

The daemon reads ~/.xdb/config.json. Switching backends is one line and a restart; nothing above the driver changes.

~/.xdb/config.json
{ "store": { "backend": "sqlite",
             "sqlite": { "path": "/var/lib/xdb/xdb.db" } } }

# memory · fs · redis · sqlite, then
$ xdb daemon restart

Schema enforcement and versioning are middleware, installed above every driver by store.New. A backend cannot skip them.

A driver is capabilities, not an interface.

Six methods on tuples and definitions, split into four roles. No Record ever crosses the boundary: the facade assembles records from tuple reads and compiles writes into mutations with their intent as data. Validation, modes and versioning all live above the line, so a new backend inherits every guarantee and cannot forget one.

  • Add Tx and batches become atomic. Add QueryTuples and filters push down to the database.
  • Add neither and everything still works: the facade runs ops one by one and filters a scan.
  • One conformance suite. Pass it and you behave like every other backend.
Operations

Six verbs. Three doors.

Get, list, create, update, upsert, delete. Call them from Go, over JSON-RPC, or in a shell. The rules, the errors and the version numbers are the same behind every door, because every door leads to the same store.

Go · in your service
rec := core.NewRecord(
    "com.example", "posts", "p-1").
    Set("title", "Hello")

err := st.CreateRecord(ctx, rec)
JSON-RPC · over the wire
{ "method": "records.create",
 "params": {
  "uri": "xdb://com.example/posts/p-1",
  "data": { "title": "Hello" } } }
CLI · in a shell or an agent
$ xdb records create \
    xdb://com.example/posts/p-1 \
    --json '{"title":"Hello"}'

Read.

Get one, list many. One CEL predicate language on every backend, compiled to SQL on SQLite. Field masks keep responses bounded. Lists return a page envelope; --page-all fetches every page and -o ndjson streams items.

xdb records get xdb://…/p-1 \
  --fields title,views

xdb records list xdb://…/posts \
  --filter 'views > 10 && !draft' \
  --fields _id,title --limit 10
{ "items": [ … ], "total": 42,
  "next_offset": 10 }

Write.

Create fails if the record exists. Update is a patch. Upsert replaces the whole record. Delete asks for --force, and deleting a schema with its records asks for --cascade too.

xdb records create xdb://…/p-1 \
  --json '{"title":"Hello"}'
# ALREADY_EXISTS if p-1 is there

xdb records update xdb://…/p-1 \
  --json '{"views":43}'    # patch
xdb records upsert xdb://…/p-1 \
  --json '{"title":"Hi"}'  # replace

xdb records delete xdb://…/p-1 --force
xdb schemas delete xdb://…/posts \
  --force --cascade

Never lose a write.

Reads return _version. A write that includes it is conditional and fails with CONFLICT if someone else got there first. Write responses report the version just stamped. Delete takes the precondition as a flag.

$ xdb records get xdb://…/p-1 -o json
{ "_id": "p-1", "_version": 3, … }

$ xdb records update xdb://…/p-1 \
    --json '{"_version":3,"title":"Hi"}'
{ "_version": 4, … }

$ xdb records delete xdb://…/p-1 \
    --force --if-version 3
{ "code": "CONFLICT", … }

Rehearse a write.

Dry run runs the full schema policy against the would-be write and writes nothing. An agent can check a payload, see the exact error it would get, and only then commit.

$ xdb records update xdb://…/p-1 \
    --json '{"views": "lots"}' --dry-run
{ "code": "SCHEMA_VIOLATION",
  "message": "type mismatch: field=views
     expected=INTEGER got=STRING", … }

$ xdb records update xdb://…/p-1 \
    --json '{"views": 43}' --dry-run
{ "dry_run": { "would": "update",
               "valid": true } }

Bulk in, bulk out.

Export a schema as NDJSON, import it back with upsert or create-only, or replay a stream of operations as one batch. A batch is atomic on SQLite and memory; on fs and redis, pass --non-atomic.

xdb export --uri xdb://…/posts \
  > posts.ndjson
xdb import --uri xdb://…/posts \
  -f posts.ndjson

xdb batch - < ops.ndjson
# {"op":"records.upsert",
#  "uri":"…","data":{…}}

Watch what changes.

Stream change events for a namespace, a schema or one record as NDJSON. Each event carries the new version, so a jump from 3 to 7 tells a subscriber it missed writes and must re-read.

$ xdb watch xdb://com.example/posts
{"ts":"…","type":"record.create",
 "uri":"xdb://…/posts/p-2","version":1}
{"ts":"…","type":"record.update",
 "uri":"xdb://…/posts/p-1","version":4}
Agents

One grammar. Agents learn it once.

Every invocation has the same shape. Resources are nouns, actions are a closed set, the URI says what you mean. There is one predicate language, one output protocol and one error shape, applied to every resource.

The manual is a command.

An agent does not need to remember the reference. It asks the CLI, and the CLI answers in the same structured output as everything else.

xdb context             # the guide
xdb describe --actions  # what exists
xdb describe records.create
xdb describe --uri xdb://…/posts
xdb describe --filter
xdb describe --errors
xdb describe --value-types
xdb describe --config

Errors are data.

Every error has the same fields in every output format, including a hint for what to try next. Exit codes are fixed: 0 ok, 1 application error, 2 connection, 3 invalid argument, 4 internal. --quiet gives you the code and nothing else.

{ "code": "NOT_FOUND",
  "message": "record not found",
  "resource": "records",
  "action": "get",
  "uri": "xdb://com.example/posts/nope",
  "hint": "try xdb records list …" }

Everything composes.

Stdin - is the explicit pipe token. Output is a table on a terminal and JSON on a pipe, or -o json|ndjson|table|yaml when you say so.

Shorthand for humans.

The URI depth picks the resource, so the short forms are macros over the full grammar. Scripts and agents use the full form; a shell uses the short one.

xdb get <uri>  → get, by URI depth
xdb ls  [uri]  → list, ns without a URI
xdb put <uri>  → records upsert
xdb rm  <uri>  → delete, with --force

Skills ship with the binary.

Recipes an agent can list and fetch at runtime: getting started, bulk data, query and filter, schema evolution. Markdown, versioned with the CLI that runs them.

xdb skills
xdb skills get bulk-data
xdb skills get schema-evolution

Discover all state.

Three list calls walk everything the daemon holds. namespaces get returns the schemas inside it, so an agent never guesses a name.

xdb namespaces list
xdb namespaces get xdb://com.example
{ "data": "com.example",
  "schemas": ["posts", …] }
xdb records list xdb://com.example

The CLI is a thin client. xdb init writes the config and starts the daemon; xdb daemon status exits 2 when it is stopped, so scripts can gate on it.

Go

A repository layer you don't have to write.

Construct a store over any driver and use it as the persistence layer of a Go service. Expose the same operations as JSON-RPC methods when you want a daemon, a sidecar or an agent endpoint. The XDB daemon is exactly that second thing.

repository.go
// Pick a backend. Policy is installed by store.New,
// never by the driver.
d, err := xdbsqlite.NewDriver(db)
st := store.New(d, store.WithSchemaCache())

// Your struct from above, or a record built by hand.
rec, err := xdbstruct.Marshal(uri, post)
err = st.CreateRecord(ctx, rec)

// Work at tuple granularity when you want to.
err = st.PutTuples(ctx,
    core.NewTuple("com.example/posts/p-1", "views", 43),
)

// Filter with CEL, project with a field mask.
page, err := st.ListRecords(ctx, &store.Query{
    URI:    core.MustParseURI("xdb://com.example/posts"),
    Filter: `views > 10 && !draft`,
    Fields: []string{"title", "views"},
    Limit:  10,
})

// Whole-batch atomicity where the driver has Tx.
err = st.(store.TX).Run(ctx, func(tx store.Store) error { … })
server.go
records := api.NewRecordService(st)
schemas := api.NewSchemaService(st)

r := rpc.NewRouter()
rpc.RegisterHandler(r, "records.create", records.Create)
rpc.RegisterHandler(r, "records.get",    records.Get)
rpc.RegisterHandler(r, "records.list",   records.List)
rpc.RegisterHandler(r, "schemas.create", schemas.Create)

http.ListenAndServe(":8147", r)
request
{ "jsonrpc": "2.0", "id": 1,
  "method": "records.list",
  "params": {
    "uri":    "xdb://com.example/posts",
    "filter": "views > 10 && !draft",
    "fields": ["title", "views"],
    "limit":  10 } }

The wire is self-describing.

The catalog behind the CLI's describe is served as RPC methods, so a client or an agent can fetch every method signature, every type and every error code from the daemon itself. Errors carry a JSON-RPC code as well as the XDB code, so a conflict is distinguishable from a not-found without parsing a message.

{ "method": "introspect.methods" }
{ "method": "introspect.method",
  "params": { "name": "records.create" } }
{ "method": "introspect.types" }
{ "method": "system.health" }
Get started

Three commands to a first record.

1Install

One Go binary. The CLI and the daemon are the same executable.

go install github.com/xdb-dev/xdb/cmd/xdb@latest
2Init

Creates the config and data dir and starts a daemon on SQLite. Switch to memory, redis or fs with one config line.

xdb init
3Write

Define a schema, write a record, read it back. Then ask describe for the rest.

xdb schemas create xdb://com.example/posts \
  --json '{"fields":{"title":{"type":"string"}}}'
xdb records create xdb://com.example/posts/p-1 \
  --json '{"title":"Hello"}'
