Typed data.
Your backend.

Store typed records in memory, files, Redis, or SQLite. XDB applies schema validation and record versioning through a Go API and an agent-oriented CLI.

Get started View GitHub
$ go install github.com/xdb-dev/xdb/cmd/xdb@latest
The model

Records are sets of tuples.

A tuple holds a typed value at a record path and attribute. Its URI lets you read or write that attribute directly.

Group records with schemas and namespaces.

Tuples with the same path form a record. The record exists while it has user attributes. A schema groups records and controls field validation. A namespace groups schemas by domain, application, or tenant.

Each resource has a URI. The available commands depend on the resource: namespaces support list and get, while records also support writes. On an attribute URI, get reads one tuple and delete removes it.

namespacexdb://com.example schemaxdb://com.example/posts recordxdb://com.example/posts/p-1 tuplexdb://com.example/posts/p-1#author.name

JSON output expands dotted attributes into nested objects. The store adds _version and _updated; the CLI also includes identity fields derived from the URI.

{ "_id": "p-1", "_ns": "com.example", "_schema": "posts",
  "_version": 1, "_updated": "2026-09-04T09:12:00Z",
  "title": "Hello", "author": { "name": "Ravi" }, "views": 42 }

Typed values.

Each backend maps XDB types to its storage format. In Go, tuple As* accessors distinguish a type mismatch from an absent attribute.

stringintegerunsignedfloatbooleantimejsonbytesarray<T>

Schema rules.

  • Declared fields are type-checked in every mode. Strict rejects undeclared fields, flexible stores them as-is, and dynamic adds their inferred types to the definition.
  • Required fields must be present and cannot be deleted from a record. On SQLite strict and dynamic schemas, indexed creates an index and unique rejects duplicate values. Other storage modes retain the declarations without enforcing them.
  • Arrays declare an element type. Object arrays can also declare fields for their items.
  • Schema updates can check a revision precondition; revision 0 skips the check. Field types and schema modes are immutable.
  • Deleting a schema and its records requires --cascade as well as --force.
Bring your own types

Import the model you already have.

Import a schema from tagged Go structs, protobuf messages, or JSON Schema documents. The adapters convert data between source types and XDB records. For protobuf and JSON Schema files, schemas diff --check compares the source with the stored definition and exits non-zero on drift.

types.go · import and use a Go type
type Post struct {
    Title  string    `xdb:"title,required"`
    Author Author    `xdb:"author"`      // → author.name
    Tags   []string  `xdb:"tags"`        // → ARRAY<string>
    Views  int64     `xdb:"views"`
}

// Import the struct definition.
def, err := xdbstruct.Def[Post]("xdb://com.example/posts")
err = st.CreateSchema(ctx, def.URI, def)

// Store a Post and read it back.
rec, err := xdbstruct.Marshal(
    "xdb://com.example/posts/p-1", post)
err = st.CreateRecord(ctx, rec)

var got Post
rec, err = st.GetRecord(ctx, uri)
err = xdbstruct.Unmarshal(rec, &got)
shell · import shows the delta, diff --check fails CI on drift
$ xdb schemas import ./api/user.proto --ns com.example
$ xdb schemas import ./user.schema.json --ns com.example
$ xdb schemas diff ./api/user.proto --ns com.example --check
go · the same importers as a library, under encoding/
def, err := xdbjson.ImportSchema(doc,
    xdbjson.WithNS("com.example"))

def, err := xdbproto.ImportMessage(md,
    xdbproto.WithNamespace("com.example"))
Backends

Choose a storage backend.

Drivers map record paths and typed attributes to backend storage. XDB includes drivers for memory, files, Redis, and SQLite. You can implement the driver contract for another backend.

Go types and SQLite column mappings.

Pick one in the config.

Set store.backend and any backend-specific options in ~/.xdb/config.json, then restart the daemon. Changing the config selects a backend; it does not migrate existing data.

~/.xdb/config.json
{ "store": { "backend": "sqlite",
             "sqlite": { "path": "/var/lib/xdb/xdb.db" } } }

# memory · fs · redis · sqlite, then
$ xdb daemon restart

store.New installs schema enforcement and versioning middleware on every driver.

Implement the driver contract.

A driver implements tuple and schema reads and writes. The store assembles records, converts writes into mutations, and applies validation and versioning. Optional interfaces add transaction support and database-side filtering.

  • Implement Tx for atomic batches and QueryTuples to evaluate filters in the database.
  • Without these capabilities, the store applies operations sequentially and filters a scan. CLI batches require --non-atomic on those backends.
  • Run the shared driver and store suites to check the contract.
Operations

Use Go, JSON-RPC, or the CLI.

Read and write records through Go, JSON-RPC, or shell commands. All use the store for validation and versioning. The API and CLI also handle request parsing, retry behavior, and output formats.

Go · in your service
rec := core.NewRecord(
    "com.example", "posts", "p-1").
    Set("title", "Hello")

err := st.CreateRecord(ctx, rec)
JSON-RPC · over the wire
{ "method": "records.create",
 "params": {
  "uri": "xdb://com.example/posts/p-1",
  "data": { "title": "Hello" } } }
CLI · in a shell or an agent
$ xdb records create \
    xdb://com.example/posts/p-1 \
    --json '{"title":"Hello"}'

Read.

Read a record by URI or filter a list with CEL. SQLite translates filters to SQL. Use field masks to select output fields. JSON and YAML lists include pagination metadata; --page-all fetches every page and -o ndjson emits one item per line.

xdb records get xdb://…/p-1 \
  --fields title,views

xdb records list xdb://…/posts \
  --filter 'views > 10 && !draft' \
  --fields _id,title --limit 10
{ "items": [ … ], "total": 42,
  "next_offset": 10 }

Write.

The CLI accepts repeated creates with identical data and returns CONFLICT for different data at an existing URI. Update patches fields; upsert replaces the record. Delete requires --force. Add --cascade to delete a schema and its records.

xdb records create xdb://…/p-1 \
  --json '{"title":"Hello"}'
# CONFLICT if p-1 differs

xdb records update xdb://…/p-1 \
  --json '{"views":43}'    # patch
xdb records upsert xdb://…/p-1 \
  --json '{"title":"Hi"}'  # replace

xdb records delete xdb://…/p-1 --force
xdb schemas delete xdb://…/posts \
  --force --cascade

Check versions before writing.

Include a non-zero _version to reject a stale write with CONFLICT. Memory and SQLite check and write atomically; filesystem and Redis have a race between those steps. Delete takes a version flag. Write responses include the resulting version.

$ xdb records get xdb://…/p-1 -o json
{ "_id": "p-1", "_version": 3, … }

$ xdb records update xdb://…/p-1 \
    --json '{"_version":3,"title":"Hi"}'
{ "_version": 4, … }

$ xdb records delete xdb://…/p-1 \
    --force --if-version 3
{ "code": "CONFLICT", … }

Validate a write.

Use --dry-run to check a payload against schema policy without writing it. The result reports validation errors or the operation that would run.

$ xdb records update xdb://…/p-1 \
    --json '{"views": "lots"}' --dry-run
{ "code": "SCHEMA_VIOLATION",
  "message": "[xdb] schema violation:
     field \"views\": cannot decode
     as INTEGER", … }

$ xdb records update xdb://…/p-1 \
    --json '{"views": 43}' --dry-run
{ "dry_run": true, "would": "update",
  "valid": true, "record": { … } }

Import, export, and batch.

Export a schema as NDJSON, import it back with upsert or create-only, or replay a stream of operations as one batch. A batch is atomic on SQLite and memory; on fs and redis, pass --non-atomic.

xdb export --uri xdb://…/posts \
  > posts.ndjson
xdb import --uri xdb://…/posts \
  -f posts.ndjson

xdb batch - < ops.ndjson
# {"op":"records.upsert",
#  "uri":"…","data":{…}}

Watch changes.

Stream changes for a namespace, schema, or record as NDJSON. Record events include a version; delete events use the last version before deletion. A version gap for the same record reveals missed writes. Delivery is at-most-once, with no replay.

$ xdb watch xdb://com.example/posts
{"ts":"…","type":"record.create",
 "uri":"xdb://…/posts/p-2","version":1}
{"ts":"…","type":"record.update",
 "uri":"xdb://…/posts/p-1","version":4}
Agents

A CLI agents can inspect.

Resource commands follow xdb <resource> <action> <URI> [flags]. Use describe to discover supported actions, payload types, filters, and error codes.

Read the built-in reference.

describe returns structured reference data. context prints the CLI guide as Markdown.

xdb context             # the guide
xdb describe --actions  # what exists
xdb describe records.create
xdb describe --uri xdb://…/posts
xdb describe --filter
xdb describe --errors
xdb describe --value-types
xdb describe --config

Handle structured errors.

Error envelopes identify the failed action and can include a recovery hint. Exit codes distinguish success (0), application errors (1), connection errors (2), invalid arguments (3), and internal errors (4).

{ "code": "NOT_FOUND",
  "message": "api: records.get …/nope:
     [xdb] not found",
  "resource": "records",
  "action": "get",
  "uri": "xdb://com.example/posts/nope",
  "hint": "try: xdb records list
     xdb://com.example/posts" }

Pipe structured data.

Pass - to read a payload from stdin. Output defaults to a table on a terminal and JSON on a pipe. Select a format with -o json|ndjson|table|yaml.

Shorthand for humans.

Aliases select a resource from URI depth. Use them for shorter shell commands or use the full resource form in scripts.

xdb get <uri>  → get, by URI depth
xdb ls  [uri]  → list, ns without a URI
xdb put <uri>  → records upsert
xdb rm  <uri>  → delete, with --force

Use bundled skills.

Fetch Markdown instructions for getting started, bulk data, filtering, and schema evolution. The skills are embedded in the CLI and available offline.

xdb skills
xdb skills get bulk-data
xdb skills get schema-evolution

Inspect stored data.

List namespaces, inspect their schemas, and list records within each namespace. Use pagination to retrieve all matching records.

xdb namespaces list
xdb namespaces get xdb://com.example
{ "namespace": "com.example",
  "schemas": ["xdb://…/posts", …],
  "total_schemas": 12 }
xdb records list xdb://com.example

The CLI is a thin client. xdb init writes the config and starts the daemon; xdb daemon status exits 2 when it is stopped, so scripts can gate on it.

Go

Embed XDB in a Go service.

Construct a store with a driver and call it from your Go service. Register API handlers on a JSON-RPC router to expose it to remote clients. The XDB daemon uses this approach.

repository.go
// Construct a store with schema enforcement and versioning.
d, err := xdbsqlite.NewDriver(db)
st := store.New(d, store.WithSchemaCache())

// Your struct from above, or a record built by hand.
rec, err := xdbstruct.Marshal(uri, post)
err = st.CreateRecord(ctx, rec)

// Work at tuple granularity when you want to.
err = st.PutTuples(ctx,
    core.NewTuple("com.example/posts/p-1", "views", 43),
)

// Filter with CEL, page with limit and offset.
page, err := st.ListRecords(ctx, &store.Query{
    URI:    core.MustParseURI("xdb://com.example/posts"),
    Filter: `views > 10 && !draft`,
    Limit:  10,
})

// Select output fields when encoding.
data, err := xdbjson.Unmarshal(rec,
    xdbjson.WithFields("title", "views"))

// Whole-batch atomicity where the driver has Tx.
err = st.(store.TX).Run(ctx, func(tx store.Store) error { … })
server.go
records := api.NewRecordService(st)
schemas := api.NewSchemaService(st)

r := rpc.NewRouter()
rpc.RegisterHandler(r, "records.create", records.Create)
rpc.RegisterHandler(r, "records.get",    records.Get)
rpc.RegisterHandler(r, "records.list",   records.List)
rpc.RegisterHandler(r, "schemas.create", schemas.Create)

http.ListenAndServe(":8147", r)
request
{ "jsonrpc": "2.0", "id": 1,
  "method": "records.list",
  "params": {
    "uri":    "xdb://com.example/posts",
    "filter": "views > 10 && !draft",
    "fields": ["title", "views"],
    "limit":  10 } }

Inspect the RPC interface.

The daemon exposes method and type catalogs through introspection RPC methods. JSON-RPC error codes distinguish conflicts from missing resources without requiring clients to parse error messages.

{ "method": "introspect.methods" }
{ "method": "introspect.method",

Get started

Create your first record.

1Install

Install the Go binary, which includes the CLI and daemon.

go install github.com/xdb-dev/xdb/cmd/xdb@latest
2Init

Create the config and start the daemon with SQLite. Select another backend in the config if needed.

xdb init
3Write

Define a schema and write a record. Use xdb describe to look up other operations.

xdb schemas create xdb://com.example/posts \
  --json '{"fields":{"title":{"type":"string"}}}'
xdb records create xdb://com.example/posts/p-1 \
  --json '{"title":"Hello"}'
